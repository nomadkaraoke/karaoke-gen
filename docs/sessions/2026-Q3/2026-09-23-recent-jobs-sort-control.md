# Recent Jobs sort control — 2026-09-23

**Project:** karaoke-gen   **Branch/commit:** `feat/sess-20260923-2207-sort-recent-jobs` → squash-merged to `main` at `0ec6909e` (PR #1042, v0.238.0)   **Status:** done — merged, deployed, verified live in prod

## Summary
Andrew asked for a way to sort the dashboard's Recent Jobs list (previously fixed newest-first) by submission date, completed date, most-recently-active date, artist, or title, in either direction. Started via `/startnomad gen ...` from the workspace root, worked in an isolated worktree, then ran the full `/shipit` pipeline through merge, deploy, and prod verification.

## What changed
- **Frontend (`frontend/app/[locale]/app/page.tsx`):** new "Sort by" `<Select>` (Submission date / Recently active / Completion date / Artist / Title) plus an ascending/descending toggle button next to the existing status-filter and results-per-page controls. Preference persisted to `localStorage` (`nomad-karaoke-sort-field`, `nomad-karaoke-sort-direction`), same pattern as the other filters. Added `data-testid="jobs-list"` to the job-cards container (was referenced by an existing test but didn't actually exist).
- **`frontend/lib/job-status.ts`:** new `sortJobs(jobs, field, direction, locale?)` utility (`JobSortField`, `SortDirection` types exported). Existing `sortJobsByDate()` (used to normalize fetch order) was left untouched — `sortJobs()` is applied on top, in the `jobs` `useMemo` in `page.tsx`, to whatever page the existing `limit`/status/search filters already fetched. It does **not** refetch or sort across the full job history.
- **Backend (`backend/services/firestore_service.py`):** added `updated_at` to `SUMMARY_FIELD_PATHS` — it was missing from the Firestore `.select()` projection used by `fields=summary` (the dashboard's normal fetch mode), so "Recently active" sorting had no data to work with until this was added.
- Tests: 13 new unit tests for `sortJobs()` (`frontend/__tests__/job-status.test.ts`), 1 new Playwright e2e test exercising the dropdown + toggle against mocked data (`frontend/e2e/regression/job-management.spec.ts`), 1 backend regression test asserting `updated_at` stays in `SUMMARY_FIELD_PATHS` (`backend/tests/test_routes_jobs.py`, same pattern as the existing `TestSummaryFieldPathsIncludesRetryPending` class).
- i18n: 8 new keys added to `frontend/messages/en.json` under `dashboard.*` (`sortBy`, `sortSubmittedAt`, `sortRecentlyActive`, `sortCompletedAt`, `sortArtist`, `sortTitle`, `sortAscending`, `sortDescending`), translated to all 33 locales via `translate.py --target all`.
- Version bumped `0.237.0` → `0.238.0` in `pyproject.toml`.
- `docs/README.md` — added a "Recent Jobs sort control" entry under Recent Changes.

## Decisions & rationale
- **No dedicated "completed" timestamp exists** on the `Job` model/Firestore doc (checked backend + summary projection + timeline — nothing tracks a discrete completion event). Rather than add a new field + backfill migration (out of scope for a UI sort feature), "Completion date" reuses `updated_at` for jobs in a terminal success status (`complete`/`prep_complete` — mirrors `frontend/lib/job-status.ts` STATUS_CONFIG's existing step-10 statuses) and pushes every other job to the end of the list regardless of direction. This is a deliberate simplification, not an oversight — worth remembering if someone later wants a *true* completion timestamp.
- **Client-side sort, not server-side.** The existing dashboard fetch (`api.listJobs`) already pulls up to `jobLimit` (5–1000) jobs ordered by `created_at desc`; `sortJobs()` just reorders that already-fetched page. Sorting by title/artist with a small `jobLimit` therefore only sorts within the most-recently-created N jobs, not the full history — consistent with how the existing limit/filter controls already behave, so no new caveat was surfaced in the UI.
- **Missing artist/title/date values always sort to the end**, regardless of asc/desc — matches common e-commerce sort-dropdown UX and avoids ambiguous placement.

## Learnings / gotchas
- **CodeRabbit CLI works fine per-review despite the known life360-org/no-seat mismatch** ([[reference_coderabbit_life360_org_mismatch]] memory note said this blocks reviews) — `coderabbit review --committed --base main` ran to completion twice in this session and found a real, legitimate issue (see below). The memory note may be stale/intermittent rather than a hard block; worth re-checking before assuming CodeRabbit is unusable in nomadkaraoke repos.
- **CodeRabbit CLI flags changed between versions** — this session's installed `0.7.6` uses `--committed`/`--uncommitted` and has no `--plain` flag (errors with "unknown option"); the `/coderabbit` skill's documented invocation (`--plain --type <type>`) is for an older CLI version. Also note: `coderabbit review` only reviews **committed** changes with `--committed` — running it before committing returns "No committed changes detected."
- **Real CodeRabbit finding, fixed:** `sortJobs()`'s artist/title `localeCompare(bValue, undefined, ...)` used the browser/runtime default locale instead of the dashboard's active `next-intl` locale — on a non-English locale route this could collate names differently than the page's displayed language (e.g. Swedish `ö` sorting). Fixed by adding an optional `locale` param threaded from `useLocale()` in `page.tsx`. Added a unit test asserting Swedish collation actually differs from the default.
- **The harness's `EnterWorktree` tool is separate from and incompatible with this workspace's `/startnomad` manual-worktree convention** — calling it created a redundant worktree under `karaoke-gen/.claude/worktrees/...` on an auto-generated branch name, conflicting with the flat-sibling/`feat/sess-*` naming this workspace's CLAUDE.md mandates. Caught immediately and undone with `ExitWorktree({action: "remove"})` before any work landed there. **Don't call `EnterWorktree` in this workspace** — worktrees are created manually per `/startnomad`'s own instructions (`git worktree add -b ... "$WORKSPACE/$FOLDER-{keywords}" origin/main`).
- **`gh pr merge --delete-branch` fails inside a git worktree** with `fatal: 'main' is already used by worktree at '...'` — it tries to locally check out `main` to delete the feature branch, but `main` is already checked out in the primary worktree. The remote merge itself still succeeds (confirmed via `gh pr view --json state`) before the local-branch-deletion step fails. Workaround: `gh pr merge --squash` (no `--delete-branch`), then delete the remote branch manually (`git push origin --delete <branch>`) and let `/cleanup`'s `git branch -D` (force, since squash-merge isn't detected as "fully merged" by `-d`) handle the local branch later from the main worktree.
- Production verification pattern confirmed working end-to-end: `docs/DEVELOPMENT.md`/`CLAUDE.md`'s admin-token + Playwright debug-script approach (`e2e/helpers/debug-prod-template.mjs`) — grabbed `KARAOKE_ADMIN_TOKEN` from Secret Manager, wrote a one-off `test-sort-control.local.mjs` (gitignored via `test-*.local.*`), logged into `gen.nomadkaraoke.com/app` with a `localStorage`-injected token, and confirmed all 5 sort options + the direction toggle render live with no new console errors.
